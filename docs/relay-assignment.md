# 中继分配：一个房间一台，到线就通知玩家换

> 状态：**已实现**（2026-10-03 定稿）。主控端：`RELAY_SET_SIZE = 1`（房间只下发一台中继）、
> `room_members.relay_node_id`（V25）、到线判定 + 通知（`promoteOverloadedRooms`）、
> **房主先切**的换台协议（`#pendingRelay`）、心跳里的 `relayChanged`。
> 客户端：中继横幅（三种 kind）+ 提示音「叮咚」（`notice-sound.ts`，并进 v1.1.0）。
> 节点侧不需要更新。

## 模型（一句话）

**房间里只连一台中继**：房主和所有成员的票据里都是**同一台**，路径恒为
`成员 → 这台 → 房主`（或成员与房主直连，更好）。这台节点负载到线时，
平台**通知玩家**，由房主切换（整房搬到更空闲的节点），其他成员重连。

## 为什么从"最多 3 台"退回 1 台

2026-09-30 曾经改成一房最多 3 台：房主连全部 3 台、每个成员分 1 台，想用"摊开负载"换吞吐。
2026-10-02 用户拿安卓端实测发现这个模型**漏了**，只有一台才能真正定死：

* 票据里的 `[[peer]]` 是**初始引导节点**，不是"只许连这些"的白名单；
* EasyTier 是张网状网：成员连上自己那台之后会通过它学到整个房间的路由表，而房主同时连着那 3 台
  —— 于是成员**照样能和另外两台建立直连**，并按代价最小选路（用户截图：成员同时握着到 3 台的
  直连，延迟 23.3 / 30.8 / 45.3 ms，每台都有流量）；
* 想让"只走分给自己那台"成立，只能靠 `avoid_relay_data`（「只协助打洞」）那个惩罚，但它的粒度是
  **节点级全局**（不是"对这个房间"），而且在我们这种"代转外来网络的 public server"形态下
  **约一半的运行里不生效、且不自愈**（复现见 `scripts/repro-easytier-avoid-relay.mjs`，结论见
  `docs/development.md` §10.5）；
* 结论：**只有"房间里只有一台中继"才能从结构上消灭误选路径**。代价明确接受 ——
  一台忙了只能整房搬走，不能把新成员摊到别的节点上。

## 到线了怎么办（用户 2026-10-03 定的流程）

"到线"有两种，都算过载（`promoteOverloadedRooms`）：

1. **这个房间自己跑出来的量** ≥ `min(平台门槛 relayScaleMbps, 该节点容量 × 它的卸荷比例)`；
2. **那台节点整体**的利用率 ≥ 它自己的卸荷线（小管子 80%、其余 90%）——
   上面还跑着别的房间，节点快满了，这个房间也该准备搬。

**两条判据各有各的窗口数**（每轮 30 秒，`advanceLoadWindows` 计数：到线 +1，掉一轮就清零重数）：

| 判据 | 轮数 | 大概多久 | 为什么 |
| --- | --- | --- | --- |
| 房间自己跑出来的量 ≥ 房间阈值 | 6 | ≈3 分钟 | 这是**瞬时吞吐**，建房/下载资源包/存档同步都会冲高，必须够久才排除抖动 |
| 那台节点**整体**利用率 ≥ 卸荷线 | 2 | ≈1 分钟 | 利用率本身已经是 3 分钟时间常数的 EWMA（`NodeUtilization`），不可能瞬时冲高；再要 3 分钟等于双重平滑，房间早就卡半天了 |

也就是说：**节点真的满了大约 1 分钟就会提示**；房间自己的流量打满则要持续约 3 分钟
（这两个数字在 `RELAY_SCALE_WINDOWS` / `RELAY_NODE_BUSY_WINDOWS`，改一处即可调）。

**先过一道闸：房间里还有人真的在走中继吗？**（`roomUsesRelay`，用户 2026-10-03 的规则
「如果房间内所有成员都是 p2p 打洞那就不发任何通知」）
判据是每个成员心跳里的 `p2p`（`resolveMemberLink` 按 EasyTier 的 `cost` 判定"到房主这条链路是不是真直连"）：

* **active 的非房主成员全部 p2p** → 流量根本不经过中继，中继忙不忙与他们无关 →
  **不发系统消息、不推横幅、不响提示音**（只记一条 debug 日志）；
* 一个成员都没有 → 同样不打扰；
* 只要有一个成员不是 p2p（或还没上报过）→ 照常通知。

过了闸之后再二选一：

| 情况 | 做什么 | 玩家看到 |
| --- | --- | --- |
| **有更空的大管子** | 准备切换目标（`#pendingRelay`），**不落库** | 房间系统消息 + `room.relayHint(kind=switch)`；**房主**的横幅是"可切换到新节点 X" + 按钮**「立即切换」**；**成员**的横幅是"可切换到新节点 X，但**需要房主更换**"，房主切完之前**没有按钮**（只留「知道了」） |
| **没得换** | 只通知，不切换（同房间 10 分钟冷却） | 房间系统消息 + `room.relayHint(kind=notice)`：「…已经到容量上限，可能会出现卡顿…目前没有更空闲的节点可以换」，两边都没有按钮 |

**文案在客户端按角色拼**（`client/src/lib/relay-hint.ts` 的纯函数 `relayHintCopy`，
回归脚本 `client/scripts/verify-relay-roles.mjs` 钉着 6 条）：服务端只下发
`kind` + `currentLabel` + `targetLabel`，因为"我该做什么"取决于收消息的人是房主还是成员 ——
同一句话发给两边，总有一边读起来别扭。

### 为什么"准备"和"生效"要分开（房主先切）

单节点模型下换台 ＝ **整房搬走**：房主的核心要连到新节点，成员才能通过新节点找到他。
如果房主还没搬、成员先搬过去，那台节点上没有到房主的路，房间直接散架。
所以：

1. 过载时只把目标记进内存（`#pendingRelay`），**房间的中继集合不变** ——
   这时候谁重连都还是旧中继，不会把自己弄丢；
2. 主控把 `kind=switch` 的提示推给房间里的所有人（房主的客户端会多出「现在切换」按钮）；
3. **房主点「现在切换」**（＝重新取票据）时，`ticket()` 才真正落库：
   `room.relayNodeIds = [新节点]` + 清空所有成员的 `relay_node_id` + 写一条房间系统消息；
4. 其他成员的**心跳**下一次就会发现"我的中继和房间当前中继不一致了"
   （`relayChanged = memberRelayStale(...)`），客户端据此弹横幅
   （`kind=apply`，按钮是「重连」）**并响一声**，点一下即可接上新中继；
5. 一直不重连的人会连不上（旧节点已经没有到房主的路）—— 所以第 3 步的系统消息
   和横幅都把这件事说清楚。

判定本体是三个纯函数（都有单测）：`relayLoadAction`（准备/只通知/别烦）、
`roomUsesRelay`（全是 p2p 就不打扰）、`memberRelayStale`（房主不算、没分配过不算、房间没中继不算）。

## 提示音（新版客户端）

`client/src/lib/notice-sound.ts`：WebAudio 现场合成的双音「叮咚」（880Hz → 587Hz，指数衰减），
**不带音频资源**（省得处理打包路径），三层保险：跟随设置页的「有人发消息时提醒我」开关、
同房间 5 秒节流、全程 try/catch 静默失败。

跟谁复用：用户要求"复用房间内有人发消息的代码通知" —— 那条链路是
`store.handleServerEvent('room.relayHint')` → `notifyPlatformHint()`（系统通知，尊重开关与聚焦判定）
→ 房间页横幅；提示音就挂在这条链路的同一个分支上，另外心跳发现 `relayChanged` 时也响一次。

## 成员分配（`pickMemberRelay`）现在还有用吗

**暂时用不上，但没有删**：房间只有一台中继时，候选池里就一台，"延迟优先 / 到线排除 / 10ms 同档"
都没有第二个对象可比。那套规则（`pickMemberRelay` + `MEMBER_RELAY_TIE_BAND_MS` +
`relayLoadPenaltyMs` 负载折价）连同单测一起留着，供"哪天集合重新变多台"时直接用；
`ticket()` 里"分到的那台还在不在池子里"这个判断与台数无关，仍然走它。
