## 房间的中继集合是"最多 3 台"

（2026-09-30 用户定的最终形态，替代过中间的"全部可调度节点"）

* **房主**：票据下发**最多 3 台**（`RELAY_SET_SIZE`）—— 手选第一台优先，其余由自动调度补齐；
* **成员**：从这 3 台里挑一台（**延迟优先**：到卸荷线的排除 → 最近的那台 → 相差 ≤10ms 取最空的，
  见文末口径），分好写回 `room_members.relay_node_id` 固定；
* 于是每个成员的路径恒为 `成员 → 它那台 → 房主`（两跳），房主的隧道数固定 ≤3。

## 要解决的问题

线上实测（`scripts/repro-easytier-avoid-relay.mjs`，探针版二进制打印了发布/接收/边表）：

* EasyTier 的 `avoid_relay_data`（「只协助打洞」）惩罚**只对"同网 peer"可靠**；
* 当那台节点是**代转外来网络的 public server**（＝我们房间的形态）时，约一半的运行里对端
  仍然选它，且 **40 秒内不自愈** —— 房间整片走那台不承载的节点、数据被丢掉；
* 结论：**不能再把"哪台承载"交给 EasyTier 选路**，必须由调度在**票据**上定死。

## 模型（两条规则）

| 角色 | 票据里的中继 | 为什么 |
| --- | --- | --- |
| **房主** | **房间的中继集合（≤3 台）** | 每台中继都有一条**直达房主**的链路；成员分配怎么变都不用房主重进 |
| **成员** | **只有分配给他的那一台** | 到房主的路只有一条 → 没有第二条可被误选的路 → 不依赖 EasyTier 那个惩罚 |

于是每个成员的路径是固定两跳：`成员 → 它的中继 → 房主`，**只有它那台在扛它自己的流量**。

```
老人 → 上海 → 房主      （上海扛它那一份）
新人 → 河北 → 房主      （河北扛，全程不碰上海）
```

### 为什么不需要"节点互为 peer"

成员之间**不需要互通**（房主开服，大家最后都是跟房主连）。所以不需要跨节点组网，
也就不需要多那一跳。已做的本地互通实验（`client1 → relayA → relayB → client2` 可达）
证明**需要时**也能做到，但本模型用不上。

## 代价（明确接受）

1. 房主会连 N 条隧道（N = 房间用到的节点数）。节点多时按区域筛一遍即可。
2. **成员之间不通**：房主开服场景无影响；若以后支持"玩家各自开服、互相直连"要另说。
3. 某成员的中继若与房主断链，该成员掉线 → 下次票据自动改分配（重进房间即可）。

## 上线节奏（一次性提示）

1. 更新主控（`git pull` + 跑一次安装脚本）。
2. **正在开的房间：让房主退出重进一次** —— 房主的旧票据里只有老中继，新成员分到另一台就到不了房主。
3. 之后**新房间全自动**：房主建房即握有全部节点，成员按负载各分一台，房主无需再重进。

## 客户端要不要更新

**不用。** 客户端只是照抄票据里的 `[[peer]]` 列表，没有"该连几台"的逻辑。

* 已知副作用（纯显示）：老客户端按 `relays[0] = 打洞节点` 贴标签 → 单中继的成员房间会显示成
  「打洞节点」（实际是中继）。下一次客户端发版把它改成"单台即中继"即可
  （`client/src/lib/relay-roles.ts`）。
* 顺手的主控端改动：`/nodes` 接口**不再下发 `assistOnly`**，老客户端那句
  「只协助打洞（不承载流量）」的提示会自动消失。

## 施工清单

> ⚠️ 本节是 **2026-09-30 当时的计划稿**（保留下来对照"当初打算怎么做"）。最终形态与它有两处不同：
> 房主票据是"房间的中继集合（≤3 台）"而不是"全部可调度节点"（`7f5ce86`）；
> 成员分配是**延迟优先**而不是"复用 `selectRelays` 的权重优先"（见文末口径）。
> 下面第 4 条的"过载换槽只影响新成员"也已随逐房间阈值一起落地。

1. **DB**：`room_members` 加一列 `relay_node_id`（nullable，老数据为 NULL = 用房间默认）。
   schema 迁移照 `server/src/db/schema.ts` 的既有风格（`alter table … add column`）。
2. **分配**：加入房间时（`RoomService.join` 那条路径）按现有排序挑一台
   —— 复用 `selectRelays` 的规则（可调度 → 未过卸荷线 → 权重优先 → 同权重比延迟 → 空余带宽）；
   **房主不参与分配**。不可用时退回 `room.relayNodeIds[0]`。
3. **票据**：`RoomService.ticket()` 按角色给集合 ——
   * 房主（`room.hostUserId === userId`）→ 全部可调度节点的 id；
   * 成员 → `[member.relay_node_id ?? room.relayNodeIds[0]]`。
4. **过载换槽**（`promoteOverloadedRooms`）：从"改写 `room.relayNodeIds`"改成
   **只影响新成员的分配**（房主集合恒为"全部"，所以不需要任何迁移/提示重进）。
   `relayScaleMbps` 默认已从 8 降到 2（`9b7d2f2`）；下一步按
   `min(平台门槛, 该节点容量 × 卸荷比例)` 逐房间取阈值。
5. **接口**：`/nodes` 去掉 `assistOnly`；`nodeSelection.roles` 保持只有 `relay`。
6. **断言**：`scripts/check-relay-slots.mjs` 增加"房主票据含全部可调度节点、成员票据只含一台"；
   `scripts/check-node-config-revision.mjs` 保持"不写 `disable_relay_data`"。
7. **文档**：`architecture.md` 调度章节、`deployment.md` §2.3.2、`troubleshooting.md` §6.6。

## 验收标准

对着一个跑起来的开发主控打真接口（`scripts/check-relay-slots.mjs` 13 项，其中 ④ 组是成员侧）：

* 房主拉票据 → `relays` = 房间的中继集合（≤3 台，逐台都直达房主）✓；
* 成员拉票据 → `relays` **只有一台**，且等于该成员被分配的节点 ✓；
* 成员带 `latencyHints` 进房 → 分到的是**他上报延迟最低**的那台（不是最空的）✓；
* 再拉一次票据 → 还是同一台（分配已固定）✓；`relay_node_id` 已落库（房主看得到）✓；
* 手动把某成员分配改成另一台 → 该成员新票据随之变化，**房主票据不变**；
* 把一台节点标为不可调度 → 新成员不再被分到它，房主票据相应减少。

## 成员分配的口径（2026-10-02 用户定的最终版）**已实现**

成员进房抽中继时（`RoomService.ticket()` 首次分配）—— 规则本体是纯函数
`pickMemberRelay`（`server/src/services/rooms.ts`，单测 9 条钉着）：

1. **到卸荷线的排出去** —— 先硬过滤掉 `utilization >= shedUtilOf(node)` 的中继 ✓
   （小管子 80%、其余 90%，与节点状态机同一条线；全过线时才退回"空余最大"并记 warn，
   不能没人可分）✓；
2. **没到线的全部按延迟优先** —— 用**该成员自己上报的 tcping 延迟** ✓
   （加入请求里带 `latencyHints`，`parseLatencyHints` 解析；老客户端不发也能进，退回"最空的"）✓；
3. **相差 ≤ 10ms 视为同一档** —— 档内取**空余带宽最大**的那台 ✓
   （档按"最快那台 + 10ms"切，即区间极差；`MEMBER_RELAY_TIE_BAND_MS = 10`）✓；
4. **没有延迟数据的中继排在最后** ✓；分好之后写回 `room_members.relay_node_id` **固定** ✓；
   已经在房的成员不会被改分配（卸荷线只约束"接新负载"，换中继要断线）✓。

三处落点：

| 在哪 | 做什么 |
| --- | --- |
| `client/src/lib/store.ts` → `joinRoom()` | 进房请求带 `latencyHints`（来自应用级测速缓存） |
| 客户端三个进房入口 | 提交前对**正在跑的**测速做一次有界等待（≤1.5s，失败/超时照常进房） |
| `server/src/api/rooms.ts` → `POST /rooms/join` | `parseLatencyHints(body)` 解析并传给 `RoomService.join` |
| `server/src/services/rooms.ts` → `join()` / `ticket()` | 暂存提示（审批制房间要等批准后才拉票据）→ 首次拉票据时 `pickMemberRelay` 分配并落库 |

> ⚠️ 需要**重新编译客户端**（v1.1.0 那批产物是在这之前打的）：不带 `latencyHints` 的老客户端
> **功能不受影响**（照样进房，退回"最空的"），但成员分中继时用不上"延迟优先"。
>
> 另注（用户实测问过）：成员在房间页看到「中继节点」列表里有多台是**正常的** ——
> 房主把房间那 ≤3 台都连上了，成员通过自己那台能**看到**其余几台；成员自己的票据里
> 始终只有 1 台（界面上只有那一台带「中继节点」角标，标题旁也写明「本机票据 N 台」）。
